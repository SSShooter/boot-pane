## bootpane M0 落地

在 Wails3 脚手架（Go 1.26 + Svelte 5 + Vite）上搭出项目启动器的骨架。

### 架构决策（已与用户确认）

- **技术栈**：沿用 Wails3，不换 Tauri/Electron。核心是管理本地进程树，Go 最合适。
- **平台**：先只做 Windows，但平台差异全部收在 `internal/pty`（Session 接口）和
  `internal/proctree`（Group 接口）后面，用 build tag 分 `_windows.go` / `_unix.go`。
  业务层禁止出现 `runtime.GOOS`。后面补 mac/Linux 只加文件不改逻辑。
- **配置双层**：全局注册表 `%APPDATA%\bootpane\workspace.json`（有哪些项目、个人覆盖层）
  + 仓库内 `.bootpane.json`（怎么启动，进 git）。合并按 `task.id`，仓库优先，
  全局层补缺并标 `origin: "local"`。
- **Agent**：规则引擎 + LLM 一起做，但两者输出共用同一个校验器（命令里的 script 必须真实存在、
  cwd 必须存在、端口不撞），生成结果先出 diff 预览再落盘。
- **日志**：内存环形缓冲 + 可选落盘。必须节流（攒 50ms 或 32KB 批量推），否则 vite 启动瞬间
  会把 Wails 事件通道打满。

### 已完成

- `internal/config`：模型、双层合并、校验（缺命令 / 依赖不存在 / 依赖成环 / 端口冲突 /

- `internal/{pty,proctree,process,discovery}`：接口 + 骨架，M1/M4 填充实现。
- `app_services.go`：ConfigService / ProcessService 暴露给前端。
- 前端：侧边栏项目列表 + 任务卡片矩阵 + 校验 banner + 空态/错误态 + toast。
- `frontend/src/lib/api.ts` 做了 API 抽象：非 WebView2 环境（纯浏览器跑 vite dev）

## M1 落地：进程管理 + 资源监控

用户截图反馈「进程管理尚未接入」，确认 M0 留下的三层全是 stub（pty/proctree/Manager），
不是差一点，是整条链路没开工。已全部实现。

### 新增结构

- `internal/win32/`（windows only）：手写 kernel32/psapi 声明。**不用 x/sys** 是因为
  CreatePseudoConsole 和 PROC_THREAD_ATTRIBUTE_JOB_LIST 在 x/sys 里没有导出。
- `internal/proctree`：Job Object（KILL_ON_JOB_CLOSE）+ Usage() 返回整树 CPU/内存。
- `internal/pty`：ConPTY，CreateProcess 一次调用同时挂 PSEUDOCONSOLE + JOB_LIST。
- `internal/process`：状态机 + 日志节流泵 + WaitFor + 1s 资源采样。

### 三个 Win32 坑（都是静默失败，排查成本极高）

1. **`CreatePseudoConsole` 的 COORD 必须按值传**。它是 4 字节结构体，x64 下塞进寄存器
   低 32 位。传指针的话系统把地址低 16 位当列数，表现是 CreateProcess 成功但子进程
   以 `0xC0000142`（DLL 初始化失败）秒退。
2. **`PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` 的 lpValue 是 HPCON 值本身，不是 &hpc**。
   传地址会把栈地址当句柄，系统直接访问违例崩溃。注意和 JOB_LIST 语义相反
   （JOB_LIST 要的是句柄数组的指针）。
3. **必须显式设 `STARTF_USESTDHANDLES` + 三个句柄为 INVALID_HANDLE_VALUE**。
   Windows 有个历史行为：即使 bInheritHandles=FALSE，标准句柄仍会被继承。不设的话，
   从终端启动时子进程继承终端的 stdout，日志全写到终端去了，ConPTY 一条收不到。
   现象极具迷惑性：进程明明在 ConPTY 里（能改窗口标题），但 echo 输出凭空消失。

### 资源监控

CPU 用 `QueryInformationJobObject(JobObjectBasicAndIOAccountingInformation)` 直接拿
整个 Job 的累计 TotalUserTime+TotalKernelTime，**天然是整树聚合**，不用枚举进程。
内存没有聚合 API，只能 `JobObjectBasicProcessIDList` 枚举 PID 再逐个
`GetProcessMemoryInfo` 求和。CPU% 按全部核心归一化（和任务管理器同口径）。

### 前端

- 事件：`bootpane:runtime` / `bootpane:log` / `bootpane:stats`，契约在 `lib/events.ts`，
  必须和 Go 侧常量逐字一致（Wails 不做校验，写错只静默收不到）。
- `lib/format.ts` 做 ANSI 剥离 + 行内回车压缩（spinner 重绘），跨块残留用 carry 续接。
- LogPanel 底部抽屉 320px，`app:has(~ .log-drawer)` 给内容区留底部空间。
- TaskCard 加 CPU/内存徽章，只在 memoryBytes > 0（有采样）时显示，避免闪 0%。

## 修复：进程退出但服务还活着，界面却显示「已停止」

用户截图反馈：任务卡片显示「已停止」，日志里却是「后端已在运行（PID 47772），跳过」。

**根因**：启动脚本自己做幂等判断——发现端口 9010 上已有服务就打印一行日志退出。
而我们的 `waitFor: port` 探测到 9010 有监听，误判成「我的进程起来了」→ running，
脚本一退出就掉回 stopped。两个缺陷：
1. `waitFor: port` 分不清「我的子进程」和「别人的进程」；
2. 进程退出后不再重新评估端口。

**方案（用户拍板：端口状态独立探测，不改状态机）**：
- 新增 `internal/portinfo`：`LookupAll(ports) []Listener`，返回 port / listening / pid / process。
- Windows 用 `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_LISTENER)`，**IPv4 和 IPv6 都查**
  （node/vite 默认监听 `::`，只查 IPv4 会漏一大半前端项目）。端口字段是网络字节序，
  要手工 `ntohs`。
- 进程名走 `QueryFullProcessImageNameW` + `PROCESS_QUERY_LIMITED_INFORMATION`，
  比读 PE 头省事，对系统进程也不失败。
- `ProcessService.CheckPorts(ports)` 暴露给前端，和 `ListRunning` 分开。
- 前端 5s 轮询（端口被谁占没法靠事件推，那个进程完全不受 bootpane 管）。

**状态文案**（关键：不能只说「已停止」）：
- `stopped` + 端口在监听 → 「已退出」+ 橙色「外部运行中」徽章
- `idle` + 端口在监听 → 「未启动」+ 同上
- tooltip 写明「端口 9010 正被 node.exe（PID 47772）占用，不是 bootpane 启动的」

测试 `internal/portinfo/portinfo_windows_test.go` 四个用例：IPv4 监听、IPv6 监听、
空闲端口、批量去重。进程名断言指向 `.test` 二进制，确认反查真的走通而不是返回空串。

## 踩坑：`npm run dev` 和 `wails3 dev` 抢 9245

用户跑 `wails3 dev` 报 `listen tcp 127.0.0.1:9245: bind: Only one usage of each socket address`。
查出来是 4 分钟前留下的 `npm run dev` 还活着（进程树 node npm-cli → cmd /d /s /c vite → node vite.js），
把 9245 占了。

根因：两条路径共用同一个端口，且都开了 `strictPort`，不会自动换端口，只会直接报错退出。
- `Taskfile.yml:7` → `VITE_PORT: '{{.WAILS_VITE_PORT | default 9245}}'`，`dev` 任务 `wails3 dev -port {{.VITE_PORT}}`
- `frontend/vite.config.ts:9` → `port: Number(process.env.WAILS_VITE_PORT) || 9245`，`strictPort: true`

也就是说 **wails3 dev 和纯 UI mock 模式天生互斥，不能同时开**。全仓库只有 3 处提到 9245
（Taskfile、vite.config、README 第 22 行）。

临时处置：Stop-Process 干掉 30772/51156/33688 三个进程，端口释放。
长期方案待用户拍板（给 mock 模式换 9246 / 什么都不改只记住别同时开）。

## 星标功能

用户要「星标的任务聚合在一起方便一起管理」。方案先给三组选项、用户拍板：
独立 stars 列表 + 侧栏固定入口 + 只做任务级（不给项目加星标）。

**数据层**（`internal/config`）：
- `Workspace.Stars []StarRef{ProjectID, TaskID}`，与 `Task` 定义完全解耦。
  关键理由：项目内配置（`.bootpane.json`）要跟仓库走、给团队共享，星标是纯个人

- `SetStar` 幂等 + 写盘失败回滚；状态没变时连盘都不写。
- `Remove()` 连带清掉该项目星标——重新添加会生成同一个 ID，不清会「诈尸」。
- `Resolve()` 拆成导出的加锁版 + 内部无锁 `resolve(p, stars)`：持锁路径
  （Projects/Get/Add）直接调后者。RWMutex 读锁可重入，但中间排进写锁就死锁。
- 5 个新测试：持久化、幂等、未知项目、移除清理、项目内配置模式下也能星标。

**前端**：
- `STARRED_VIEW = "__starred__"` 保留 id 当伪项目；`load()` 里要特判，否则
  「选中项不存在就回退到第一个项目」会把星标视图踢掉。
- `starredTasks` 派生扁平列表 `{project, task}[]`；`toggleStar` 只改本地那份
  `starredTaskIds`，不整表重拉（重拉会换对象，日志面板和滚动位置会抖）。
- `startTask` 返回值改成 `Promise<boolean>`，批量启动靠它统计失败数。
- `StarredPanel.svelte` 刻意不按项目分组：星标的用途就是把散落的按钮拉到一起，
  再套一层分组反而拉远距离；项目名做成卡片上的小徽章。
- 卡片星标按钮 `opacity: 0` 常驻占位，hover/已星标才显形——用 opacity 不用
  display，否则标题可用宽度变化会让省略号位置跳。
- 星标用琥珀色 `--star`，不和主色蓝的「启动/停止」抢层级（它是状态不是动作）。


## 编辑配置（启动项增删）

用户说「添加删除项目功能」，实际指的是截图里那些**启动项卡片**这一层；
添加方式用户自己指定为「编辑 json」，不要表单。追加两个决策：repo 模式
允许直接写仓库文件；卡片上不加删除入口，一切都在 JSON 弹窗里完成。

**核心设计：单一写入入口。** 没有做 `UpsertTask`/`DeleteTask` 这类细粒度方法——
那样等于两套写入路径，校验逻辑要写两遍，迟早出现「单条删除绕过校验」。
新增 / 修改 / 删除全部走 `SaveConfigJSON(id, raw)`。

**Go 侧**：
- `Store.ConfigSnapshot(id)`：repo 模式返回仓库文件**原文**（用户可能自己排过版，
  反序列化再序列化会搅乱格式）；文件不存在时给空骨架。全局模式从注册表拼 ProjectFile。
- `Store.ApplyConfig(id, pf, syncMeta)`：按当前配置来源写 workspace.json 或
  `.bootpane.json`（tmp + rename 原子写，写完 tmp 不能残留）。
- `ConfigService.applyConfig(p, pf, syncMeta, failMsg)`：`ImportTasks` 和
  `SaveConfigJSON` 共用。两者差异只有两处——空 tasks 允不允许、项目名/标签
  跟不跟着走（导入传 false，大模型编的名字不能覆盖用户认得的名字）。
- `ParseProjectFile` 保留「必须至少一个 task」；新增 `ParseEditableConfig`
  允许空列表。删光启动项是正常操作。
- 校验仍然全在后端。删掉一条被 pipeline 引用的任务会被 `Validate` 挡下，
  这正是「删除也走同一入口」白捡的好处。
- 6 个 store 测试 + 5 个 service 测试。注意：测试文件里已有 `writeRepoConfig`
  辅助函数，写入函数只能叫 `writeRepoFile`，同包同名会编译失败。

**前端**：
- `ConfigEditor.svelte`：等宽 textarea + 格式化 + 前端 JSON 语法预检
  （只拦明显写坏的，真正的校验在后端）+ Ctrl+S 保存 + 有改动时关闭要确认。
- `ProjectPanel` 头部加「编辑配置」，空状态里加「手写 JSON」。
- **`.dialog-wide` 必须给死 height，不能只给 max-height**：容器高度由内容决定时
  `.dialog-body` 的 `flex: 1` 没有可分配空间，textarea 会缩成一条。
- textarea 用 `white-space: pre` + 横向滚动，不折行——JSON 折行会把层级读乱。

**验证方式**：playwright-cli 没装，改用 **CDP 直接驱动 headless Chrome**
（`--remote-debugging-port`，Node 22 自带全局 WebSocket/fetch），
跑通了「打开弹窗 → 改坏 JSON → 提示 + 保存禁用 → 改好 → 保存 → 卡片数变化 →
重开读到新值」11 项断言。比纯截图强得多，值得复用。

其余几条：

- `env` 只在示例里出现、字段说明里没有 → 模型会写 `PORT=5173 pnpm dev`。
  Windows 下 `cmd.exe /d /s /c` 执行，这种前缀赋值直接失败（见 `pty_windows.go`）。
- `waitFor` 缺兜底。拿不准端口时模型会猜，猜错 → 60s 后 `fail` 把任务标成 failed，
  但 `fail` 只改状态不杀进程，用户看到「失败」而服务是活的。
  正确做法是**省略 waitFor**（`awaitReady` 的 nil 分支 = 进程起来就算跑着）。
- `waitFor.log` 是 `strings.Contains` 大小写敏感子串，不是正则。prompt 没写。
- 输出格式约束夹在中间，应挪到末尾。
- 没区分「常驻进程」和「一次性脚本」，模型会把 lint/build/test 也列上。
- 缺「找不到入口就输出空 tasks」的兜底，模型会硬编。
- 平台信息缺失。要注入 shell 描述的话，按项目约定不能业务层写 `runtime.GOOS`，
  应该在 `internal/pty` 加带 build tag 的 `ShellDescription()`。
